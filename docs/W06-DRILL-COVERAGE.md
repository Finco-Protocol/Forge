# W06 — Incident drill coverage (13 scenarios)

Evidence class: `SANDBOX` — every drill runs the real application code against a local Anvil, in-process Postgres (PGlite), a fake GitHub and test keys. A drill proves the **application's containment behaviour and the alert signal it computes** (`src/server/ops/monitor.ts`, 20 rules). It does **not** prove that any alert reaches a person: production monitoring, paging and contact routing do not exist in this repository and remain **operator item B06 (Class B)**. Nothing below claims otherwise.

Existing drills: `apps/forge-web/test/integration/w05-incident-drills.test.ts` (13 tests executing runbook §D1–§D15 — §D7, §D8, §D12 are cross-referenced to other suites — `docs/W05-INCIDENT-RUNBOOK.md`). W06 adds drills **only** for scenarios that file did not execute: `apps/forge-web/test/integration/w06-incident-drills.test.ts` (8 tests).

## 2. Alert-rule honesty check (from running the signals, W06)

| Rule | Status |
|---|---|
| `DEEP_REORG` | **Dead signal** — no writer of `ALERT:reorg*` (pinned by an `it.fails` drill) |
| `WEBHOOK_BACKLOG` | **Cannot fire in production** — the handler inserts the delivery row and processes it in one transaction, so an unprocessed row is never committed (a failed delivery rolls back and leaves no trace). The rule logic itself works on a hand-inserted row (asserted). Failed deliveries are invisible to monitoring; GitHub's redelivery is the only recovery |
| `ALERT:signer_*` audit events | Written, but no rule reads them |
| No rule | stuck pending transaction; rejected webhook signatures; PostgreSQL unavailability (needs an external probe) |

These are reported, **not fixed** (product freeze).
